# Write a Blog Post

按顺序推进以下流程。将大纲确认和发布确认作为两次明确的人工检查点；未获得对应确认时停在当前阶段。

## 1. 梳理 idea 并对齐大纲

1. 阅读用户提供的 idea、笔记、草稿和相关材料。
2. 检查仓库中的相关旧文，了解已有观点、项目背景和可以自然承接的内容。
3. 搜索与 idea 直接相关的信息，澄清必要的外部上下文、近期变化和关键概念。此处只做形成大纲所需的探索，不提前展开完整调研。
4. 梳理文章要表达的核心内容、面向的读者和各部分之间的逻辑关系。缺少关键的个人经历、判断或创作意图时，向用户提问，不代替用户编造。
5. 提出标题方向和大纲，说明每一部分准备讲什么。根据内容自然组织结构，不套用固定文章框架。
6. 与用户修改并敲定大纲。获得明确确认后再进入后续阶段。

## 2. 按需收集信息

根据已确认大纲判断是否需要继续调研：

- 当文章主要基于用户的经历、观点或已提供材料，且事实依据已经足够时，跳过深入调研。
- 当文章依赖外部事实、数据、论文、产品现状、行业趋势或多方观点时，使用 `$deep-research` 收集并核验信息。
- 只缺少少量事实时，进行针对性搜索和原文核验，不扩大为不必要的完整调研。

围绕大纲收集信息，记录可追溯来源、争议和无法确认的内容。若调研结果实质改变文章的核心判断或结构，先向用户说明并重新对齐大纲。

## 3. 撰写文章

1. 完整阅读 `references/shared-style.md`，并阅读与文章主题最相关的历史文章。
2. 按已确认的大纲写作。保证逻辑顺畅、表达简洁、通俗易懂，并符合 Tom 的语言习惯。
3. 区分用户的观点与外部事实。不要编造个人经历、判断、数据或引用；不确定之处明确标出并向用户确认。
4. 为外部事实保留准确链接，让引用能够回溯到实际支持该表述的来源。
5. 按仓库现有约定生成 front matter、slug、分类、标签和必要的内部互链，并将草稿写入 `source/_posts/` 下合适的位置。
6. 检查全文是否围绕核心内容推进，删除重复、空泛、跳跃或过度解释的段落。

完成草稿不代表获得发布许可。此阶段不要 commit 或 push。

## 4. 与用户最终对齐

1. 告知用户草稿路径并概括文章的核心表达。
2. 列出仍需确认的个人表述、事实、引用或结构选择。
3. 根据用户反馈持续修改，直到内容无误。
4. 明确询问是否可以发布。只有用户清楚表达“可以发布”或同等意思时，才进入发布阶段。

## 5. 发布到 GitHub

1. 确认当前分支是 `main`。如果不是，告知用户并停止，不自行设计其他发布流程。
2. 检查 `git status` 和 diff，只纳入本次文章及用户确认需要一同发布的文件，保留其他已有改动。
3. 运行 `npm run build`，修复由本次文章引起的构建问题。
4. 在 `main` 上创建描述准确的 commit。
5. 直接执行 `git push origin main`。
6. 向用户报告文章路径、构建结果、commit 和 push 结果。

如果构建、提交或推送失败，报告具体原因并继续处理可安全修复的问题；不要宣称已经发布。
